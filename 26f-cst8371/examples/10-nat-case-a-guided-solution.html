The case

Intended behaviour. Each host on LAN-A should get its own public address from the pool 198.51.100.17 – .30 when it goes outside. LAN-B is not translated.

What you are told. After clear ip nat translation *, PC-A (192.168.100.10) pings the server 192.0.2.69 and gets 100% loss. On EDGE, show ip nat translations is empty.

Your task. Find the first step that fails, say which evidence proves it, write the smallest fix on the right router, and say how you would verify it.

Addressing plan
PC-A  192.168.100.10 and .11 /25
      gateway 192.168.100.126 (EDGE Eth0/2)
PC-B  172.16.100.10 /28 (LAN-B, no NAT)
EDGE  Eth0/1 203.0.113.100/24  outside
      Eth0/2 192.168.100.126/25 inside
      Eth0/3 172.16.100.14/28  no NAT role
ISP   Eth0/1 203.0.113.254/24
      ACL BLOCK-RESERVED in (private sources)
SERVER 192.0.2.69/24
NAT design on EDGE
Eth0/1  ip nat outside
Eth0/2  ip nat inside
access-list 10 permit 192.168.100.0 0.0.0.127
ip nat pool LANA-POOL 198.51.100.17
  198.51.100.30 netmask 255.255.255.240
ip nat inside source list 10 pool LANA-POOL
(no overload: one address per host)

The design is what the network should look like. The evidence below is what the devices actually show. The fault is in the gap between them.

The steps, in order

  1. Traffic generated
  2. Selected for translation
  3. Resource available
  4. Translation occurring
  5. Return traffic allowed
  6. Make the change
  7. Verify the change

Steps 1–5 are the NAT troubleshooting checklist. Work them in order, before you change anything. The first step that fails is where you look for the fault. You still check the later steps, because they show what the fault is not. Step 6 is the repair and step 7 is the proof that it worked.

Steps 1–7

  1. Traffic generated not checked

    Before blaming NAT, prove the test traffic was valid: the right source, a way to the gateway, and a path onward from the router.

    Exhibit
    PC-A
    [01]PC-A$ ip addr show eth0 | grep inet inet 192.168.100.10/25 scope global eth0 inet 192.168.100.11/25 scope global secondary eth0
    [02]PC-A$ ip route default via 192.168.100.126 dev eth0 192.168.100.0/25 dev eth0 scope link
    [03]PC-A$ ping -c 3 192.0.2.69 3 packets transmitted, 0 packets received, 100% packet loss
    EDGE
    [04]EDGE# show ip route 192.0.2.69 Routing entry for 0.0.0.0/0, supernet * 203.0.113.254
    [05]EDGE# ping 203.0.113.254 !!!!! Success rate is 100 percent (5/5)

    A failed ping tells you something is wrong, not where. Ask two things: from which address did the packet leave PC-A, and does PC-A know the way to the router that will translate it?

    That matches the evidence. [01] shows the test source is a LAN-A address and [02] shows the default gateway is EDGE's inside interface, as the plan says. [04] and [05] show EDGE can reach the outside. The ping failing is the symptom you were handed, not a fault in this step.

    Look again. Compare [01] and [02] with the addressing plan. Is the source a LAN-A address? Is the gateway the one the plan names? Then read [04] and [05]: can EDGE reach the outside? If all of that is in order, the test traffic is valid and the failed ping is only the symptom.

  2. Selected for translation not checked

    NAT only translates traffic it selects. Selection has two parts: the interface roles, and the rule that says which source addresses are chosen. Compare both with the design.

    Exhibit (EDGE)
    [06]EDGE# show ip nat statistics Total active translations: 0 (0 static, 0 dynamic; 0 extended) Outside interfaces: Ethernet0/1 Inside interfaces: Ethernet0/2 Hits: 0 Misses: 0
    [07](same command, lower part) Dynamic mappings: -- Inside Source [Id: 1] access-list 10 pool LANA-POOL refcount 0 pool LANA-POOL: netmask 255.255.255.240 start 198.51.100.17 end 198.51.100.30 type generic, total addresses 14, allocated 0 (0%), misses 0
    [08]EDGE# show access-lists 10 Standard IP access list 10 10 permit 192.168.10.0, wildcard bits 0.0.0.127

    An ACL that exists is not the same as an ACL that matches. Put the design text next to the device text and compare them one number at a time, not just line by line.

    That matches the evidence. [06] shows both roles are present, so the roles are not your problem. Now look at [08] next to the design's access-list 10 line.

    Which number is different? Write down the range that ACL actually permits, then decide whether PC-A's address is inside it. That is the question to answer before you move on.

    Look again. Selection has two parts. First check the roles in [06] against the design. Then read [08] against the design's access-list 10 line, one number at a time. Ask whether PC-A's address would be selected by what [08] actually says.

  3. Resource available not checked

    Dynamic NAT with a pool needs addresses to give out. Check the pool exists, has addresses free, and sits inside the public block the ISP routes (198.51.100.16/28).

    Exhibit (EDGE)
    [07](from step 2) -- Inside Source [Id: 1] access-list 10 pool LANA-POOL refcount 0 pool LANA-POOL: netmask 255.255.255.240 start 198.51.100.17 end 198.51.100.30 type generic, total addresses 14, allocated 0 (0%), misses 0

    Count the addresses and compare the start and end with the public block. Then ask what "allocated 0" means: a pool that is empty, or a pool nobody has used yet?

    That matches the evidence. The pool is defined, it has 14 addresses, none are in use, and the range is inside the block the ISP routes. The resource is there and ready. It is simply unused, and step 2 already suggests why.

    Look again. Check three things in [07]: the pool exists, it has addresses free, and the start and end fall inside 198.51.100.16/28. Zero allocated means nothing has used the pool yet, which is different from a pool that cannot give out addresses.

  4. Translation occurring not checked

    This is before you make any change: the configuration is still as supplied, and the ping from PC-A has just failed. Look for proof that a translation was made, and for what the next device actually received.

    Exhibit (captured after the failed ping, before any change to the configuration)
    EDGE
    [09]EDGE# show ip nat translations (no entries)
    ISP
    [10]ISP# show access-lists BLOCK-RESERVED Standard IP access list BLOCK-RESERVED 10 deny 10.0.0.0, wildcard bits 0.255.255.255 20 deny 172.16.0.0, wildcard bits 0.15.255.255 30 deny 192.168.0.0, wildcard bits 0.0.255.255 (3 matches) 40 deny 169.254.0.0, wildcard bits 0.0.255.255 50 deny 127.0.0.0, wildcard bits 0.255.255.255 60 permit any

    An empty translation table is a symptom, not a cause. Read [10] and ask: did the ISP receive packets with private or public sources? Which line counted them?

    That matches the evidence. No translation was made [09], and the ISP counted packets with a private source on its deny line [10]. The packets left EDGE untranslated.

    This step fails because of what you found in step 2, not on its own. The fault is in the earliest failing step, so that is where the fix belongs.

    Look again. [09] is empty, so was anything translated? In [10], which line is counting, and what kind of source address does that line match? Packets that leave EDGE with their original private source tell you translation did not happen.

  5. Return traffic allowed not checked

    A translation also needs a way back. The ISP must know how to reach the public pool addresses.

    Exhibit (ISP)
    [11]ISP# show ip route 198.51.100.16 Routing entry for 198.51.100.16/28 Known via "static", distance 1, metric 0 * 203.0.113.100

    A route to the pool is half of a return path. Can you prove replies come back when no packet was ever translated?

    That matches the evidence. The route in [11] is in place, so the return setup is ready. But with nothing translated there is no reply traffic to observe, so you cannot prove the return path yet. You will test it after the fix.

    Look again. [11] shows a route to the pool block, so the ISP knows where to send replies. Ask what that proves when no translated packet was ever sent. A route is ready; it is not the same as replies arriving.

  6. Make the change not checked

    Change as little as possible, on the device where the first failing step lives. Before you type anything, keep the evidence you collected in steps 1 to 5: the failed ping, the NAT statistics, the ACL text and the ISP counters. It proves what was wrong.

    The fix belongs where your earliest failing step lives. Then ask what happens to the wrong line that is already in the list: does adding a new line remove it?

  7. Verify the change not checked

    A fix is only proved by the same kind of evidence that showed the fault. Clear the old state, repeat the test that failed, then read the evidence from steps 2 to 4 again.

    Think about the two hosts on LAN-A (.10 and .11) and about the design: each host should get its own address from the pool. A ping alone does not show which address was used. What else can you read on EDGE?

    Exhibit: expected shape after the change
    [12]PC-A$ ping -c 3 192.0.2.69 3 packets transmitted, 3 packets received, 0% packet loss PC-A$ ping -c 3 -I 192.168.100.11 192.0.2.69 3 packets transmitted, 3 packets received, 0% packet loss
    [13]EDGE# show ip nat translations Pro Inside global Inside local Outside local Outside global --- 198.51.100.17 192.168.100.10 --- --- --- 198.51.100.18 192.168.100.11 --- --- (matching icmp entries appear while the ping runs)
    [14]EDGE# show ip nat statistics Total active translations: 2 pool LANA-POOL: total addresses 14, allocated 2 (14%), misses 0

    Compare with the PAT demo: there is no shared address and there are no port numbers. Control: PC-A to PC-B (172.16.100.10) works before and after, because LAN-B was never part of the NAT design.

How I will see this in a quiz question
Practice formatQuestion – NAT Selection: Find / Fix / Verify

On the in-class quiz you do not get the guide. You get the case, the numbered evidence and an answer sheet. The question asks for the same work you just did, in this order:

  • Find: the first step that fails, the evidence lines that prove it, and a one or two sentence diagnosis (steps 1 to 5).
  • Fix: the device and the complete commands (step 6).
  • Verify: the command you would run and what you expect to see (step 7).

Try it now, without the step cards: use the case and the exhibits [01]–[11] above, fill every field, then press Check my answers. Marks go per field, so an empty field is a lost mark. Cite only the lines that prove your answer. The sheet checks for key words, not your exact wording.

Worked answer
first_failing_step=
2 (selected for translation)
evidence_lines=
[08] against the design's access-list 10 line; [06] shows the roles are fine
diagnosis=
ACL 10 permits 192.168.10.0/25, not 192.168.100.0/25, so PC-A is never selected, nothing is translated, and the ISP drops the private source.
repair=
On EDGE: configure terminal / no access-list 10 / access-list 10 permit 192.168.100.0 0.0.0.127
verify_command=
PC-A: ping -c 3 192.0.2.69 and ping -c 3 -I 192.168.100.11 192.0.2.69; then EDGE: show ip nat translations
verify_expected=
0% loss; one entry per host, each with a different address from 198.51.100.17 – .30; pool allocated 2. No port numbers, unlike PAT.

Before you change anything, keep the failed ping, show ip nat statistics, show access-lists 10 and the ISP counters. They are your proof of what was wrong.

Common mistakes
Stopping at "the ACL exists"An ACL has to match the right addresses. Compare it to the design one number at a time.
Blaming the first thing that looks oddRun all five steps. Each step you rule out with a line makes your diagnosis stronger.
Treating the symptom as the causeAn empty translation table and a failed ping describe what you see. They do not say why.
Fixing the wrong deviceEvidence that sits on the ISP does not mean the fault is on the ISP. Fix where the earliest failing step lives.
Half a commandName the device, then give every command IOS needs, in the order you would type them.
Verifying with the wrong toolA ping alone does not show what was translated. Check the translation table too.

The case

Intended behaviour. Host 192.168.100.10 (A-10) should always appear outside as 209.165.200.226 and reach the server 192.0.2.69. No other host is mapped.

What you are told. On EDGE, show ip nat translations shows entries for 192.168.100.10. From PC-A, ping -c 3 192.0.2.69 shows 100% loss, and wget -q -O - -T 3 http://192.0.2.69/ times out.

Your task. Say what the translation entries prove and what they do not. Find the first step that fails, say which evidence proves it, write the smallest fix on the right router, and say how you would verify it.

Addressing plan
PC-A  192.168.100.10 and .11 /25
      gateway 192.168.100.126 (EDGE Eth0/2)
PC-B  172.16.100.10 /28 (LAN-B, no NAT)
EDGE  Eth0/1 203.0.113.100/24  outside
      Eth0/2 192.168.100.126/25 inside
      Eth0/3 172.16.100.14/28  no NAT role
ISP   Eth0/1 203.0.113.254/24
      ACL BLOCK-RESERVED in (private sources)
SERVER 192.0.2.69/24
Public block for NAT: 209.165.200.224/29
  .226 = A-10
NAT design on EDGE
Eth0/1  ip nat outside
Eth0/2  ip nat inside
ip nat inside source static
  192.168.100.10 209.165.200.226
(one for one, permanent, A-10 only)

The design is what the network should look like. The evidence below is what the devices actually show. The fault is in the gap between them.

The steps, in order

  1. Traffic generated
  2. Selected for translation
  3. Resource available
  4. Translation occurring
  5. Return traffic allowed
  6. Make the change
  7. Verify the change

Steps 1–5 are the NAT troubleshooting checklist. Work them in order, before you change anything. The first step that fails is where you look for the fault. You still check the later steps, because they show what the fault is not. Step 6 is the repair and step 7 is the proof that it worked.

Steps 1–7

All evidence in steps 1 to 5 was captured before any change to the configuration.

  1. Traffic generated not checked

    Before blaming NAT, prove the test traffic was valid: the right source, a way to the gateway, and a path onward from the router.

    Exhibit
    PC-A
    [01]PC-A$ ip addr show eth0 | grep inet inet 192.168.100.10/25 scope global eth0 inet 192.168.100.11/25 scope global secondary eth0
    [02]PC-A$ ip route default via 192.168.100.126 dev eth0 192.168.100.0/25 dev eth0 scope link
    [03]PC-A$ ping -c 3 192.0.2.69 3 packets transmitted, 0 packets received, 100% packet loss PC-A$ wget -q -O - -T 3 http://192.0.2.69/ (no output: timed out)
    EDGE
    [04]EDGE# show ip route 192.0.2.69 Routing entry for 0.0.0.0/0, supernet * 203.0.113.254
    [05]EDGE# ping 203.0.113.254 !!!!! Success rate is 100 percent (5/5)

    A failed ping and a timed-out web request tell you something is wrong, not where. Ask two things: from which address did the packet leave PC-A, and does PC-A know the way to the router that will translate it?

    That matches the evidence. [01] shows the test source is a LAN-A address and [02] shows the default gateway is EDGE's inside interface, as the plan says. [04] and [05] show EDGE can reach the outside. The failures in [03] are the symptom you were handed, not a fault in this step.

    Look again. Compare [01] and [02] with the addressing plan. Is the source a LAN-A address? Is the gateway the one the plan names? Then read [04] and [05]: can EDGE reach the outside? If all of that is in order, the test traffic is valid and the failures are only the symptom.

  2. Selected for translation not checked

    NAT only translates traffic it selects. Here the selection is the static mapping, plus the interface roles. Compare both with the design.

    Exhibit (EDGE)
    [06]EDGE# show ip nat statistics Outside interfaces: Ethernet0/1 Inside interfaces: Ethernet0/2 Hits: 9 Misses: 0
    [07]EDGE# show running-config | include ip nat ip nat inside source static 192.168.100.10 209.165.200.226

    Put the design text next to the device text and compare them one number at a time. Check the roles first, then the mapping: the inside address and the outside address.

    That matches the evidence. [06] shows the roles are where the design puts them. [07] is the design's mapping, number for number. Nothing here is selecting the wrong traffic.

    Notice what you have not proved yet: that the translated traffic gets where it is going and comes back.

    Look again. Check the roles in [06] against the design. Then read [07] against the design's mapping line, one number at a time: the inside address and the public address. If they match, selection is working.

  3. Resource available not checked

    Static NAT does not use a pool. Its resource is the mapping itself: the permanent entry that ties the inside host to the public address. Check that the entry exists and uses the address the design names.

    Exhibit (EDGE)
    [08]EDGE# show ip nat translations Pro Inside global Inside local Outside local Outside global --- 209.165.200.226 192.168.100.10 --- ---

    A permanent entry with no ports and no outside address is the mapping waiting to be used. Does it name the inside host and the public address from the design?

    That matches the evidence. The permanent entry is there and it ties 192.168.100.10 to 209.165.200.226. The resource exists and is ready.

    Look again. The first line of [08] is the permanent mapping. Does it name the inside host and the public address the design gives? If so, the resource is in place.

  4. Translation occurring not checked

    This is still before you make any change, with the failed ping and web request behind you. Look for proof that translations were made while the test ran, and for what the next device received.

    Exhibit (captured after the failed tests, before any change to the configuration)
    EDGE
    [09]EDGE# show ip nat translations Pro Inside global Inside local Outside local Outside global --- 209.165.200.226 192.168.100.10 --- --- icmp 209.165.200.226:1 192.168.100.10:1 192.0.2.69:1 192.0.2.69:1 tcp 209.165.200.226:40213 192.168.100.10:40213 192.0.2.69:80 192.0.2.69:80
    ISP
    [10]ISP# show access-lists BLOCK-RESERVED Standard IP access list BLOCK-RESERVED 10 deny 10.0.0.0, wildcard bits 0.255.255.255 20 deny 172.16.0.0, wildcard bits 0.15.255.255 30 deny 192.168.0.0, wildcard bits 0.0.255.255 40 deny 169.254.0.0, wildcard bits 0.0.255.255 50 deny 127.0.0.0, wildcard bits 0.255.255.255 60 permit any (6 matches)

    Read [09] for the entries made while the ping and the web request ran, then read [10] and ask which line counted packets. Was the source address private or public when it reached the ISP?

    That matches the evidence. EDGE made translations for the ping and the web request [09], and the ISP counted the packets on its permit any line, not on a deny line [10]. The source address was already public.

    This is the trap in this case: translation is present and still the tests fail. A working translation only proves translation. It does not prove the request was answered or that the reply came back.

    Look again. [09] lists entries for the ping and the web request, so was anything translated? In [10], which line counted the packets, and what does that say about the source address the ISP received?

  5. Return traffic allowed not checked

    A translation also needs a way back. Three questions: did the request reach the server, did the server answer, and can the answer find its way back to the translated address?

    Exhibit
    ISP
    [11]ISP# show ip route 209.165.200.226 % Network not in table
    [12]ISP# ping 209.165.200.226 ..... Success rate is 0 percent (0/5)
    SERVER
    [13]SERVER$ netstat -an | grep ':80' tcp 0 0 0.0.0.0:80 0.0.0.0:* LISTEN tcp 0 0 192.0.2.69:80 209.165.200.226:40213 SYN_RECV

    Follow one packet. The request left EDGE with a public source. [13] shows what the server did with it. Then ask which address the server must now send its answer to, and whether the ISP, the next device on that path, knows how to reach it.

    That matches the evidence. [13] shows the request arrived and the server started to answer. The answer goes to 209.165.200.226, and [11] and [12] show the ISP has no way to reach that address.

    This is the first step that fails, so this is where the fault lives. The NAT rule on EDGE is not what is wrong.

    Look again. [13] shows the request reached the server. The server must now answer the address in its connection table. Read [11] and [12]: can the ISP reach that address? What happens to a packet when a router has no route for its destination?

  6. Make the change not checked

    Change as little as possible, on the device where the first failing step lives. Before you type anything, keep the evidence you collected in steps 1 to 5: the failed ping and web request, the EDGE translations, the ISP route lookup and the SERVER connection table. It proves what was wrong.

    A route needs a destination, a mask and a next hop. The public block is in the addressing plan. Which router must learn it, and which neighbouring address leads to the device that owns it?

  7. Verify the change not checked

    A fix is only proved by the same kind of evidence that showed the fault. Repeat the tests that failed, then read the evidence from steps 4 and 5 again.

    Two things failed at the start: a ping and a web request. Repeat both from the host that failed. Then read the one line on the ISP that was missing before the change.

    Exhibit: expected shape after the change
    [14]PC-A$ ping -c 3 192.0.2.69 3 packets transmitted, 3 packets received, 0% packet loss PC-A$ wget -q -O - -T 3 http://192.0.2.69/ SERVER 192.0.2.69 web ok
    [15]ISP# show ip route 209.165.200.226 Routing entry for 209.165.200.224/29 Known via "static", distance 1, metric 0 * 203.0.113.100

    Controls: PC-A to PC-B (172.16.100.10) works before and after. Two results stay as designed and are not faults: PC-A's second address (ping -c 3 -I 192.168.100.11 192.0.2.69) is not mapped, so it goes out untranslated and the ISP drops it; and PC-B to 192.0.2.69 fails for the same reason.

How I will see this in a quiz question
Practice formatQuestion – NAT Return Path: Find / Fix / Verify

On the in-class quiz you do not get the guide. You get the case, the numbered evidence and an answer sheet. The question asks for the same work you just did, in this order:

  • Find: the first step that fails, the evidence lines that prove it, and a one or two sentence diagnosis (steps 1 to 5).
  • Fix: the device and the complete commands (step 6).
  • Verify: the command you would run and what you expect to see (step 7).

Try it now, without the step cards: use the case and the exhibits [01]–[13] above, fill every field, then press Check my answers. Marks go per field, so an empty field is a lost mark. Cite only the lines that prove your answer. The sheet checks for key words, not your exact wording.

Worked answer
first_failing_step=
5 (return traffic allowed)
evidence_lines=
[11] (no route on the ISP), supported by [13] (the request reached the server)
diagnosis=
The static mapping works: EDGE translates, and the server received the request. The ISP has no route to the inside global address 209.165.200.226, so the server's reply is dropped at the ISP.
fix_command=
On ISP: configure terminal / ip route 209.165.200.224 255.255.255.248 203.0.113.100
verify_command=
PC-A: ping -c 3 192.0.2.69 and wget -q -O - -T 3 http://192.0.2.69/; ISP: show ip route 209.165.200.226
verify_expected=
0% loss; wget prints SERVER 192.0.2.69 web ok; the ISP lists a static route to 209.165.200.224/29 via 203.0.113.100.

Common mistakes
Stopping at "the translation is there"A translation only proves that translation happened. Delivery and the return path need their own evidence.
Changing the NAT ruleIf the mapping matches the design and the entries appear, the NAT rule is not the fault. Look further along the path.
Fixing the router where the symptom showsThe failing ping starts on PC-A, but the fault lives on the device where the first failing step is, here the ISP.
Treating the symptom as the causeA failed ping and a timed-out request describe what you see. They do not say why.
Half a commandA route needs the destination, the mask and the next hop, and you name the device it goes on.
Verifying with only one testRepeat everything that failed: the ping and the web request. Then read the route that was missing.
